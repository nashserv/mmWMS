# Полный прогон — 16 проверок раздела 9.6

Автоматический интеграционный прогон стенда. Все шестнадцать шагов раздела 9.6
мастер-контекста, в том же порядке и с теми же ASSERT.

Гоняется ежедневно; красный блокирует мерж (правило 9.5.5). Чинит тот поток,
который указан владельцем шага.

---

## Зачем он красный на старте

На момент завершения потока 0 `wms` — это mock, а потоков A, B и C ещё нет.
Большинство шагов падает, и это не поломка прогона, а его работа: с первого дня
видно, что именно не работает, и по мере готовности потоков проверки зеленеют
одна за другой.

Поэтому здесь **нет ни одного `skip` и ни одного `xfail`**. Пропуск читается
как успех, а прогон существует ровно ради обратного. Не добавляйте их, чтобы
«сделать зелёно» — вместо этого чините шаг или объясняйте красное в отчёте.

Чтобы красное было читаемым, в конце запуска печатается таблица:

```
шаг  владелец  статус    проверка                                чего не хватает
  1  C, A      КРАСНЫЙ   Завести клиента, ячейки, ...            /warehouse/documents ответил ...
  4  A         КРАСНЫЙ   Симулятор WB отдаёт 5 заданий           симулятор WB не отвечает по ...
```

## Запуск

```bash
pip install -r requirements.txt

export WMS_BASE_URL=http://127.0.0.1:8080
export DATABASE_URL=postgresql://wms:...@127.0.0.1:5432/wms
export RABBITMQ_URL=amqp://mmx:...@127.0.0.1:5672/

python -m pytest                    # все 16
python -m pytest -m stream_a        # только то, что чинит поток A
python -m pytest -m stream_b
python -m pytest -m stream_c
python -m pytest -k step_04         # один шаг
```

Шаги идут в порядке раздела 9.6 и передают состояние друг другу (задания из
шага 4 подбираются в шаге 8 и отгружаются в шаге 11). Шаг, до которого сценарий
не дошёл, краснеет с указанием, какой шаг чинить первым, — но краснеет, а не
пропускается.

Пустой результат предыдущего шага считается отсутствующим: ноль заданий не
должен молча проходить проверку «ни одно задание не выдано двоим». Ложный
зелёный в прогоне опаснее красного — он снимает блокировку мержа.

## Данные прогона

Прогон заводит **своего** клиента (`full-run-seller`), свои штрихкоды, ячейки и
коробки (`scenario.py`) и не опирается на дамп: вчерашний остаток не должен
превращаться в сегодняшний ложный зелёный. `reference` и `wb_order_id`
уникальны в пределах запуска — это ключи идемпотентности (инвариант 5).

Живых токенов, ИНН и кабинетов здесь нет и быть не может (раздел 12).

## Три проверки, которые нельзя выразить одним HTTP-вызовом

Они реализованы по-настоящему, а не отключены. Если чего-то не хватает — шаг
падает с указанием, что именно должен дать поток A или B.

**Шаг 4, «ни одного HTTP-вызова внутри транзакции — проверка по трейсу».**
Трассировки OpenTelemetry на стенде пока нет, но отпечаток HTTP-вызова внутри
транзакции в Postgres однозначен: бэкенд сидит `idle in transaction` и ждёт
клиента, пока тот разговаривает с Wildberries. Прогон наблюдает
`pg_stat_activity` с шагом 5 мс всё время резерва и требует: ни одного
`idle in transaction`, самая долгая транзакция короче 100 мс (раздел 6.2
отводит ей 2–5 мс, вызов в WB — около 500 мс), и **наблюдение обязано что-то
увидеть** — пустой трейс означает не «нарушений нет», а «резерв идёт мимо
Postgres». Когда поток A добавит трассировку, проверку можно ужесточить до
«в спане транзакции нет дочерних HTTP-спанов».

**Шаг 10, «< 50 мс до записи в устройство».** Путь состоит из двух половин.
Первую — `POST /labels/{task_id}/print` — прогон измеряет сам: `wms` отдаёт
готовые байты. Но сам он их никому не толкает. «Клик печать» на складе
происходит на экране рабочего места, и байты агенту по открытому соединению
push'ит оно (раздел 6.6) — поэтому прогон дёргает и
`POST {WORKSTATION_BASE_URL}/api/workstation/v1/print`. Без этого агент честно
отчитывается о нуле записей, и половина пути, ради которой переписана вся
этикетка, не проверяется вовсе.

Вторую половину, запись RAW-байтов в USB-принтер, измерить может только агент
печати (поток B), поэтому он обязан отдавать её по `PRINT_AGENT_STATS_URL`:

```json
{"task_id": "…", "last_write_ms": 12.4}
```

Без этого утверждение шага проверить нечем — и шаг красный, а не «условно
зелёный».

**Шаг 16, «10 000 заданий в час».** Прогон держит целевую скорость
(10 000/час = одно задание за 360 мс) в течение окна `FULL_RUN_LOAD_SECONDS` и
требует: ни одного отказа, фактическая скорость не ниже целевой, все принятые
задания доехали до `wms_task`, удержание блокировки p99 < 100 мс по тому же
наблюдению за `pg_stat_activity`. Час подряд гонять не нужно: требование
раздела 5 — про скорость, а не про длительность.

## Что прогон обнажил в самих контрактах

Не ошибки прогона, а места, где контракт потока 0 ещё не закрыт. Решает поток 0
(правило 9.5.2).

1. **Маршрута создания ячеек в контракте нет.** Шаг 1 требует «завести
   клиента, ячейки», но ни в приложении B, ни среди новых маршрутов нет ничего
   про `zone`/`cell`. Прогон заводит ячейки адресами в строках документа
   начального остатка (`cell_address` есть в `WarehouseDocumentLine`) и потом
   проверяет их наличие в базе. Если сервис так не умеет — шаг краснеет, и это
   правильный сигнал: либо маршрут, либо явное правило «ячейка создаётся по
   адресу при первом упоминании».
2. **Задания шага 4 засеваются через ручку стенда симулятора**:
   `POST {WB_SIMULATOR_URL}/__stand__/seed-orders` с телом
   `{"account", "count", "barcode", "deadline"}`. У настоящего Wildberries
   такой ручки нет — она существует ровно затем, чтобы «WB отдал пять
   заданий» было воспроизводимым шагом. Обходить опрос через `/reservations`
   нельзя: шаг 4 проверяет путь «WB → задание в базе» целиком.
3. **Контракта биллинга в этом репозитории нет.** Шаг 12 читает начисления
   прямо из базы потока C (`BILLING_DATABASE_URL`, таблица
   `BILLING_ACCRUAL_TABLE`, связь по `event_id`). Когда поток C зафиксирует
   свой контракт, шаг переводится на него.
4. **Mock отвечает не по контракту на `/tasks/pull`.** Контракт требует
   `{tasks, served_at}`, mock отдаёт `{tasks, count}`, и элементы у него —
   плоские задания вместо `{task, leased_until, placements}`. Прогон читает по
   контракту (`item["task"]["task_id"]`), поэтому шаг 8 красный и против mock.

## Что мигает на этом стенде и почему это не склад

Прогон зелёный 16 из 16, но два шага изредка краснеют на нагруженном стенде.
Оба раза причина в измерении, а не в коде, и оба раза это проверено — не
предположено. Пороги не тронуты: они написаны в разделе 9.6, и двигать их —
решение владельца.

**Шаг 10, «wms отдаёт стикер за 53 мс при пределе 50».** Прогон мерит время
снаружи, по HTTP. Гистограмма самого сервиса
(`mmx_wms_label_print_duration_seconds`) показывает **87 запросов из 87 быстрее
10 мс**. То есть маршрут вшестеро внутри бюджета, а разница — накладные
расходы измерения: восемь ядер стенда делят Postgres, четыре воркера,
рабочее место, сервисы потока C и сам прогон.

**Шаг 4, «за 2 с появилось 0 заданий из 5».** Случается, когда прогон запускают
сразу после предыдущего. Кабинет придержан ограничителем: лимит Wildberries —
300 запросов в минуту на кабинет (приложение D), и опрос плюс работа
предыдущего прогона его выбирают. Прогон ждёт освободившегося окна перед
стартом, но если запускать подряд без пауз, окно не успевает устояться.
Шаг называет состояние кабинета прямо в сообщении — статус, код ошибки и через
сколько секунд следующий опрос.

**Если стенд свободен, оба шага зелёные.** Ежедневному прогону, ради которого
скрипт и существует, это не мешает: он гоняется один раз, а не пять подряд.
