## Тесты сервисов и база стенда

Юнит-тесты `services/wms` гоняются против **`wms_test`**, а не против рабочей
`wms`:

```bash
export WMS_TEST_DATABASE_URL=postgresql://wms:...@127.0.0.1:5432/wms_test
cd services/wms && python -m pytest -q
```

Причина не в чистоте ради чистоты. Рядом с рабочей базой крутятся настоящие
воркеры — опрос Wildberries, стикеры, сверка. Против общей базы тест и воркер
разбирают одни и те же задания: тест краснеет «опросчик завёл 3 из 5», хотя
сломан не он. И каждый прогон оставляет в базе своего продавца и свой кабинет
WB; опросчик берёт по восемь кабинетов за тик, так что через несколько сотен
прогонов полный круг перестаёт укладываться в две секунды — и краснеет уже
полный прогон, шагом 4, по причине, которая с шагом 4 никак не связана.

Полный прогон (`tests/full-run`) — наоборот, идёт против рабочей `wms`: он
проверяет стенд целиком, вместе с воркерами.

## Ворота на живые токены

Раздел 12 мастера: **на стенде нет живых токенов WB. Ни одного.**

Живой токен на стенде отправит настоящие команды в кабинет клиента — создаст
поставку, переведёт задание в собранное, перезапишет остатки. Это необратимо,
и узнает об этом клиент, а не мы.

Поэтому проверка — не пункт регламента, а сервис `token-guard`, который
стартует первым. Пока он не завершится с кодом 0, ни один другой сервис не
поднимется (`condition: service_completed_successfully`).

Что он ищет в `./dump` и `./env`:

- значения формы JWT (`eyJ...` в три сегмента) — токены WB это именно JWT;
- присвоения вида `WB_TOKEN=`, `api_key:`, `secret_ref=` с непустым значением.

Что он считает нормальным: `test-token-*`, `development-only-*`, `change-me`,
`vault://`, `${VAR:?set outside Git}`.

Проверить руками, не поднимая стенд:

```bash
./scripts/check-no-live-tokens.sh ./dump ./env
```

Коды возврата: `0` — чисто, `1` — найдено, `2` — проверять было нечего
(пустая проверка не считается пройденной). Найденные значения **не печатаются**
— иначе секрет утёк бы в лог CI.

## Обезличенный дамп

Снимается **вручную человеком с доступом** к боевому контуру. Compose его не
вызывает и без него поднимается — mock работает на своих фикстурах.

```bash
PROD_DSN_GATEWAY=postgresql://readonly@91.108.239.175:5432/wb_gateway \
PROD_DSN_CATALOG=postgresql://readonly@91.108.239.175:5432/catalog \
PROD_DSN_BILLING=postgresql://readonly@91.108.239.175:5432/billing \
./scripts/dump-from-prod.sh
```

Выгружает: кабинеты (`sellers`, `wb_accounts`), каталог (`catalog_product`,
`catalog_mapping`), задания за неделю, тарифы.

Два свойства, ради которых он написан именно так:

1. **Обезличивание в самом запросе.** `secret_ref` заменяется на
   `test-token-{n}` при выгрузке. Файла с живыми токенами не возникает на
   диске ни на секунду — иначе он останется в бэкапе ноутбука и однажды в Git.
2. **`BEGIN TRANSACTION READ ONLY`.** Боевой контур только на чтение (раздел
   12). Даже опечатка в запросе не сможет ничего записать — проверено:
   `UPDATE` внутри такой транзакции падает с `cannot execute UPDATE in a
   read-only transaction`.

По окончании дамп прогоняется через те же ворота. Не прошёл — удаляется
целиком, потому что это ошибка в запросах обезличивания, а не повод чистить
руками.

## Сервисы платформы

Пункт 6 файла 01 требует поставить на стенд `fbs-operator-workstation`,
`product-catalog`, `billing`, `portal*`, `internal-admin`, `identity` — as-is
из платформы, направив их `WMS_ADAPTER` на mock `wms` вместо Odoo.

**Их нет в `compose.yaml`, и это осознанно:** исходники лежат на боевом
сервере (`/root/MM-express-final-platform-integration`), в этом репозитории
их нет. Выдумывать их описание значит записать в стенд неправду.

Порядок подключения, когда исходники будут доступны:

1. Скопировать каталоги сервисов в `services/` этого репозитория.
2. Дописать их в `compose.yaml` по образцу сервиса `wms`.
3. Каждому выставить:
   ```yaml
   WMS_ADAPTER: http
   ODOO_WMS_URL: http://wms:8080/api/mmx/wms/v1
   ```
   Контракт `/api/mmx/wms/v1/*` сохранён специально ради этого — под него уже
   написаны клиенты (раздел 6.7 мастера).
4. Базы для них уже создаются: `scripts/create-databases.sh` заводит
   `wb_gateway`, `workstation`, `catalog`, `billing`, `returns`, `portal`,
   `internal_admin`, `identity` при первом старте Postgres.

Аналогично `wb-simulator`: пункт 6 предписывает взять существующий из
платформы. Здесь лежит минимальный, написанный по приложению D. Когда
платформенный станет доступен — заменить: за ним боевые прогоны, за этим нет.

## Полный прогон

16 проверок раздела 9.6 мастера:

```bash
cd ../../tests/full-run
WMS_BASE_URL=http://127.0.0.1:8080 \
DATABASE_URL=postgresql://wms:...@127.0.0.1:5432/wms \
python -m pytest -v
```

**На старте потока 0 большинство проверок красные, и это правильно.** `wms` —
заглушка, поэтому шаги, которые требуют настоящей транзакции, нагрузки и
трейсов, падают. Скрипт с самого начала показывает, чего именно ещё нет; по
мере готовности потоков A/B/C проверки зеленеют одна за другой.

Срез по потоку: `pytest -m stream_a`.

## Что стенд НЕ делает

- Не ходит в боевой контур. Ни один сервис compose не знает адреса
  `91.108.239.175`. Единственная связь — ручной запуск `dump-from-prod.sh`.
- Не имеет живых токенов WB и не умеет их принять: `token-guard` не пустит,
  а схема `wb_account` не примет `secret_ref` формы JWT.
- Не публикует ничего в настоящий Wildberries. Только `wb-simulator`.
