# Shadow-контур — раздел 11, шаг 2

**Не запущен.** Здесь лежит всё, чтобы его поднять, и ничего, что его
поднимает.

---

## Стоп-линия

> Никакой деплой, push или изменение боевого контура **без явного разрешения
> владельца** (раздел 12). Раздел 11 требует переключать **по одному кабинету,
> не пачкой**, и разрешение нужно на каждый шаг отдельно — одного на всю
> миграцию не бывает.

Этот каталог покрывает **только шаг 2**: опрос на чтение и ежедневный отчёт
расхождений. Шаги 3–6 (начальный остаток, публикация остатков, полный цикл,
все кабинеты) здесь не готовятся.

---

## Что сделано, чтобы писать в кабинет было нечем

Защита не на дисциплине, а на четырёх независимых вещах. Любой одной хватило
бы; их четыре, потому что цена ошибки — необратимая запись в кабинет живого
клиента, о которой узнает он, а не мы.

1. **Режим кабинета.** `wb_account.mode = 'shadow'`, и `wb.writes_allowed()`
   пропускает запись только если окружение локальное **И** `WB_API_URL` пуст.
   Здесь `APP_ENV=production` и адрес задан — не выполнено ни одно.
2. **Воркера стикеров в контуре нет.** Запрос стикера кладёт заказ в поставку,
   то есть пишет.
3. **Брокера нет вообще.** Публикатор outbox отправил бы события shadow в
   боевую шину, и биллинг выставил бы клиенту счёт **второй раз** за те же
   заказы. Без `RABBITMQ_URL` опубликовать их физически нечем.
4. **База своя.** Отдельный том, порт наружу не публикуется.

Проверяется это не чтением файла, а скриптом, который спрашивает сам код:

```bash
cd infrastructure/shadow
cp .env.example .env      # заполнить
./scripts/preflight.sh
```

`.env` в оболочку **не подгружать**. `set -a && . ./.env` кладёт токены и
пароли в окружение вашей оболочки и оттуда — в историю, в дочерние процессы, в
дамп при отладке. Compose читает `.env` сам; preflight читает конфигурацию
через `docker compose config` и спрашивает секрет у самого сервиса, а не у
вашей оболочки.

Девять проверок. Одна не прошла — не поднимать.

## Порядок

**1. Спросить владельца.** Какой кабинет первый и сколько запросов в минуту
тратит на него боевой шлюз (**вопрос 11 раздела 13 — открыт**).

**2. Посчитать бюджет.** Лимит 300 запросов в минуту на кабинет ОБЩИЙ с боем:

```bash
./scripts/poll-budget.py --prod-rpm <сколько тратит бой>
```

Выдаст `SHADOW_POLL_INTERVAL_SECONDS`. Наугад это число не ставить.

**3. Клапан «собрать без остатка» выключать не нужно — он и так выключен.**

С 13.09.2026 умолчание `allow_ledger_short` — `false` (миграция 011, решение
владельца: расхождений быть не должно вовсе). Раньше здесь стоял обязательный
`UPDATE`, и это было признаком неверного умолчания: когда первым шагом
развёртывания идёт «отключить умолчание», выбрано оно неправильно.

Проверить, что так и есть, всё же стоит — база могла приехать из дампа
постарше:

```sql
SELECT seller_external_id, allow_ledger_short FROM owner;
```

Почему это важно именно в shadow: остаток приезжает только на шаге 3, то есть
здесь его нет ни у кого. С включённым клапаном **каждое** теневое задание
создало бы расхождение `ledger_short` и событие `wms.stock.shortfall.v1` —
неделя ложных тревог поверх настоящих. С выключенным задание встаёт в `short`:
видимое, счётное и ровно такое, какое и должно быть, когда товара по учёту нет.

**4. Положить файл секрета.**

Токен лежит файлом в каталоге, который монтируется контуру **на чтение**.
Имя файла — это `secret_ref` кабинета, приведённый к имени файла: из
`vault://mmx/wb/seller-42` получается `mmx-wb-seller-42`.

```bash
mkdir -p /srv/mmwms-shadow-secrets
umask 077
printf '%s' '<токен кабинета>' > /srv/mmwms-shadow-secrets/mmx-wb-seller-42
# В .env: WB_SECRET_HOST_DIR=/srv/mmwms-shadow-secrets
```

Каталог не в Git и не в репозитории вовсе. `printf` без перевода строки:
лишний `\n` в конце токена — это 401 от Wildberries и полдня поисков.

**5. Завести клиента и кабинет — через API, не SQL.**

Контур поднимается пустым: миграции создают схему, данных в ней нет. Владелец
и кабинет заводятся теми же маршрутами, что и везде, на петлевом адресе:

```bash
BASE=http://127.0.0.1:18080/api/mmx/wms/v1
call() { curl -sS -X POST "$BASE$1" -H 'content-type: application/json' \
              -H "authorization: Bearer $SHADOW_SERVICE_TOKEN" \
              -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"params\":$2}"; }

call /sellers '{"seller_external_id":"seller-42","name":"ИП Иванов"}'
call /wb/accounts '{"op":"upsert","external_id":"wb-42",
                    "seller_external_id":"seller-42",
                    "display_name":"Кабинет 42",
                    "secret_ref":"vault://mmx/wb/seller-42",
                    "mode":"shadow","status":"ACTIVE"}'
```

`mode: shadow` обязателен. `secret_ref` — ссылка, не токен: схема не примет
значение формы JWT.

**6. Импортировать каталог кабинета.**

Без товаров каждое теневое задание встанет в `manual_review` («товара нет у
владельца»), и отчёт расхождений будет состоять из них одних — см.
`docs/05-shadow-readiness.md`.

```bash
# Карточки кабинета из Content API — это ЧТЕНИЕ, в shadow разрешено.
call /catalog/wb-cards '{"seller_external_id":"seller-42","limit":500}'
# Завести товары по штрихкодам из ответа:
call /catalog/products/ensure '{"seller_external_id":"seller-42",
                                "barcode":"4600000000011"}'
```

**7. Преflight, потом подъём.**

```bash
./scripts/preflight.sh && docker compose -f compose.shadow.yaml up -d
```

**8. Читать отчёт расхождений. Минимум неделя** (раздел 11).

Отчёт ложится в таблицу `shadow_divergence_report`, а не только в лог: неделю
наблюдения сравнивают посуточно, а лог ротируется и исчезает вместе с
контейнером. Вопрос недели один — **убывает ли разница**:

```sql
SELECT observed_on,
       sum(tasks)  AS расхождений,
       count(*)    AS пар_владелец_товар
  FROM shadow_divergence_report
 GROUP BY observed_on
 ORDER BY observed_on;
```

Что именно разошлось за последний день:

```sql
SELECT seller_external_id, barcode, state AS у_нас, wb_status AS у_wb, tasks, oldest
  FROM shadow_divergence_report
 WHERE observed_on = current_date
 ORDER BY tasks DESC
 LIMIT 20;
```

Самая частая пара будет `cancelled` / `complete` — то самое расхождение
боевого контура на 2467 заданий (раздел 3). Если в shadow её нет, значит
новая WMS видит заказы там, где старая их теряла, и это главный результат
шага 2.

Отчёт, который никто не открывает, от молчания отличается мало.

## Откат

```bash
./scripts/rollback.sh
```

На шаге 2 откат дешёвый: shadow ничего не писала, боевой шлюз кабинет не
терял и о нас не знал. Данные остаются — отчёт за наблюдение это единственный
результат шага 2.

## Чего здесь нет и это надо знать заранее

**`catalog-stock-worker` продолжает писать остатки в те же кабинеты.** Раздел
6.3 его упраздняет, раздел 6.8 отдаёт публикацию остатков `wms`. На шаге 2
безвредно — в shadow мы не публикуем ничего. **Но до шага 4 развести
обязательно**, иначе два сервиса будут писать в один кабинет разные числа.
Исходников `product-catalog` в репозитории нет (см.
`services/wms/FINDINGS.md`, находка 11).

**Формат этикетки не подтверждён живым принтером** — вопрос 2 раздела 13. На
шаге 2 не мешает: стикеры не запрашиваются вовсе. К шагу 5 обязан быть закрыт.
