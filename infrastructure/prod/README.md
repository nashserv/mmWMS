# Боевой контур — шаги 4–6 раздела 11

**Ничего отсюда не запускается без явного разрешения владельца на конкретный
шаг и конкретный кабинет** (раздел 12). Переключение идёт по одному кабинету,
не пачкой.

## Чем отличается от стенда

| | стенд | здесь |
|---|---|---|
| `check-no-live-tokens.sh` | ворота: живой токен — авария | **нет вовсе**: живой токен — смысл работы |
| Симулятор WB | есть | нет, `WB_API_URL` обязателен |
| Сиды | есть | нет: клиенты и тарифы заводятся через API |
| Тестовые базы | есть | нет |
| Роли Postgres | включены задним числом | с первого дня |
| `APP_ENV` | `development` | `production` — от него зависят запреты, а не логи |
| Умолчания в `.env` | есть | **нет ни одного**: compose не поднимется без переменной |

Стендовые ворота здесь не забыты, а убраны намеренно. На стенде живой токен
означает, что прогон отправит настоящие команды в кабинет клиента. Здесь он
означает, что контур работает. Те же ворота на бою не дали бы подняться вовсе,
а причину искали бы в сети.

## Порядок

**1. Заполнить `.env`** по `.env.example`. Все переменные обязательны, включая
две, которые не про технику:

- `PROD_OWNER_APPROVAL` — на какой шаг и какой кабинет получено разрешение и
  когда. Преflight без этой строки контур не пустит.
- `PROD_PRINTER_CONFIRMED` — проверен ли формат этикетки на живом принтере
  (вопрос 2 раздела 13). На шаге 4 стикеры не запрашиваются — там годится
  «шаг 4, не требуется».

**2. Завести роли Postgres** — `../stand/scripts/create-roles.sh`, по одному
паролю на сервис. Роли зовутся `svc_*`: имя без префикса совпало бы с
владельцем баз, и смена пароля переписала бы пароль суперпользователя.

**3. Положить токен кабинета файлом** в `WB_SECRET_HOST_DIR` под `umask 077`.
Имя файла — это `secret_ref`, приведённый к имени файла: из
`vault://mmx/wb/seller-42` получается `mmx-wb-seller-42`. Без перевода строки
в конце: лишний `\n` — это 401 и полдня поисков.

**4. Посчитать частоту опроса.** У кабинета 300 запросов в минуту ВСЕГО, и
боевой шлюз уже их тратит:

```bash
../shadow/scripts/poll-budget.py --prod-rpm <сколько тратит бой>
```

**5. Преflight, потом подъём.**

```bash
./preflight.sh && docker compose -f compose.prod.yaml up -d
```

Десять проверок, и каждая отвечает на вопрос «что сломается, если этого не
сделать», а не «красиво ли настроено».

## Откат

```bash
./rollback.sh
```

Гасит сначала то, что ПИШЕТ в Wildberries, и только потом остальное: пока
воркеры живы, каждая секунда добавляет расхождение с боевым шлюзом, который
вот-вот заберёт кабинет обратно. Данные не удаляются — по ним разбирают
причину.

Возврат кабинета боевому шлюзу — вручную и с отдельным разрешением владельца.

## Чего здесь нет и это надо знать заранее

**`catalog-stock-worker` на боевом сервере продолжает писать остатки в те же
кабинеты.** Пока он жив, два сервиса будут писать в один кабинет разные числа.
До шага 4 развести обязательно. Исходников `product-catalog` в этом
репозитории нет.

**Агент печати живёт не в контуре**, а на компьютере оператора: он говорит с
USB-принтером. В `prometheus.yml` его адрес помечен `ЗАМЕНИТЬ-НА-АДРЕС-СТОЙКИ`
и до замены цель будет красной — это лучше, чем убрать её и не заметить, что
печать не наблюдается вовсе.

**Контур ни разу не поднимался.** Он собран, `compose config` его разбирает,
преflight отрабатывает на заполненном `.env`, но живого запуска не было и быть
не могло: для него нужен доступ к бою.
