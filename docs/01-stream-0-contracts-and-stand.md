# Поток 0 — контракты и стенд

**Перед этим файлом прочитать целиком:** `00-master-context.md`. Всё ниже опирается на разделы того документа без повтора.

**Кто:** один исполнитель. **Срок:** 2–3 дня. **Когда:** до старта потоков A, B, C — они не могут начать без результатов этого потока.

**Ветка:** работа идёт в `main` или в `stream-0`, но результат должен попасть в `main` до того, как A/B/C создадут свои ветки от него.

---

## Миссия

Заморозить то, о чём три параллельных агента не должны спорить между собой: схему данных, контракт API, каталог событий. Поднять стенд, на котором это всё проверяется. Написать mock, чтобы потоки B и C не ждали поток A.

Если этот поток сделан плохо или расплывчато — три агента потом либо дублируют работу, либо спорят о контракте вместо того, чтобы его использовать. Точность здесь окупается многократно.

---

## Что сделать, по порядку

### 1. Схема базы `wms`

Взять целиком раздел 7 мастер-контекста. Написать миграции (тот же стиль, что у существующих сервисов — см. раздел 2.2 мастера, `migrations/`). Проверить каждый инвариант раздела 8 на уровне схемы, где это возможно:

- `stock_move.idem_key UNIQUE` — есть
- триггер, запрещающий `UPDATE`/`DELETE` на `stock_move` — написать явно, не полагаться на дисциплину кода
- `wms_task.cancel_reason` — `NOT NULL` только когда `state='cancelled'` (constraint или триггер)
- `owner_id` — внешний ключ везде, где упомянут в разделе 7

**После написания — заморозка.** Дальше изменения только через этот же поток, синхронно всем трём.

### 2. Контракт `wms` — OpenAPI

Файл `services/wms/contracts/openapi.yaml`. Состав:

- 29 маршрутов из приложения B мастера (сверено дословно с `@http.route` в `mmx_wms_bridge/controllers/api.py` на проде — совпадение полное, один в один) — пути и формы запросов взять из приложений B и C дословно. Это не новое проектирование, это перенос существующего контракта на новый сервис
- Новые маршруты из того же приложения B: `/tasks/pull`, `/labels/{task_id}/print`, `/receipts/screen`, `/putaway/screen`, `/wb/accounts`, `/wb/accounts/{id}/verify`
- Схемы ошибок — коды из приложения C («Коды ошибок резерва») как enum, не как свободная строка

### 3. Каталог событий — AsyncAPI

Файл `services/wms/contracts/asyncapi.yaml`. Взять полный список `wms.*` и `inventory.*` из приложения A, схемы из приложения E. Добавить новое: `wms.stock.shortfall.v1` (раздел 6.5 мастера) — по образцу существующих payload из приложения E, с полями `owner_id`, `sku_id`, `cell_id`, `qty_short`, `task_id`.

Envelope — как в разделе 2.4 мастера, без отклонений.

**Правило порядка (приложение E, последний абзац):** `outbox.sequence` инкрементируется в той же транзакции, что и движение. Зафиксировать это как требование к реализации в контракте (комментарий в AsyncAPI), не только прозой.

### 4. Таблица маппинга статусов

Один файл (`docs/state-mapping.md` или таблица в контракте) с четырьмя колонками:

| `wms_task.state` | статус рабочего места | канонический статус | статус WB |
|---|---|---|---|

Взять состояния из раздела 7 мастера (автомат задания) и раздела 2.12 (маппинг WB), состояния рабочего места из раздела 3 диагностики (`queued/picking/picked/printed/packed/boxed/shipped/closed/cancelled`). Это таблица, на которую будут ссылаться все три потока — не оставлять пробелов.

### 5. Mock сервиса `wms`

FastAPI-заглушка с теми же путями, что в OpenAPI, отвечающая заранее зафиксированными телами ответов (можно захардкодить фикстуры). Должна:

- отвечать на `/reservations` с `status: "reserved"` для известных тестовых SKU и `PRODUCT_MAPPING_MISSING` для неизвестных
- эмитить события в RabbitMQ в правильном формате (приложение E), чтобы потоки B и C могли писать консьюмеры уже сейчас
- отвечать на `/tasks/pull` списком фикстур-заданий

Потоки B и C работают против этого mock, пока поток A не готов.

### 6. Стенд

Сервер: `151.245.140.225` (приложение F мастера). Доступ по ключу `musik-personal`, пароль отключён.

Поднять через Docker Compose:

- Postgres 16.10, база на сервис (как в разделе 2.2)
- RabbitMQ 4.1.2, exchange `mmx.events`
- `wms` (mock из п. 5)
- `wb-simulator` — взять образ/код из платформы (раздел 2.3 мастера, он уже существует и используется в проде для тестов)
- `fbs-operator-workstation`, `product-catalog`, `billing`, `portal*`, `internal-admin`, `identity` — скопировать as-is из платформы, направить на `WMS_ADAPTER` в сторону mock `wms` вместо Odoo
- Prometheus + Grafana — минимальный набор дашбордов на метрики из раздела 10 (критерии «идеально»)

**Перед первым запуском — обязательная проверка (раздел 12 мастера):**

```bash
# Ни одного живого токена WB в дампе или конфиге стенда
grep -rE "wb_account_secrets|WB_TOKEN|api_key" <дамп и env-файлы> 
# должно быть пусто или только заглушки вида "test-token-xxx"
```

Если найдётся хоть один похожий на настоящий JWT — стенд не запускать, пока не заменён.

### 7. Обезличенный дамп

Из боевой базы (только чтение, `91.108.239.175`) выгрузить:
- кабинеты (`sellers`, `wb_accounts` — без `secret_ref`/токенов, заменить на `test-token-{n}`)
- SKU (`catalog_product`, `catalog_mapping`)
- задания за неделю (для реалистичного объёма при тестах)
- тарифы (`billing_tariff`, `billing_tariff_version`)

Все ИНН/токены/секреты — заглушки. Имена продавцов можно оставить или обезличить, на работу не влияет.

### 8. Шаблон сервиса и линтер

Скопировать структуру `wb-fbs-gateway` (раздел 2.2 мастера) как отправную точку для `services/wms/`. Тот же `Dockerfile` (Python 3.13-slim, `USER 65532`), тот же набор зависимостей, тот же линтер/форматтер, что уже используется в репозитории.

### 9. Скрипт полного прогона

Реализовать все 16 проверок из раздела 9.6 мастера как автоматический тест (pytest или аналогичный, интеграционный, гоняется на стенде целиком). На старте потока 0 большинство ASSERT будут падать, потому что `wms` — это mock. Это нормально: скрипт с самого начала показывает, что именно ещё не работает, и по мере готовности потоков A/B/C проверки зеленеют одна за другой.

Гонять этот скрипт — обязанность каждого потока перед мержем (правило 9.5 мастера, пункт 5).

## Готово когда

- миграции применяются на чистой базе без ошибок, все инварианты раздела 8 проверены на уровне схемы, где применимо
- OpenAPI и AsyncAPI валидны (проходят линтер спецификации), покрывают все 29+6 маршрутов и все события
- таблица маппинга статусов не имеет пустых ячеек
- mock отвечает на все маршруты и эмитит все события из каталога
- стенд поднимается одной командой (`docker compose up`), проверка на живые токены встроена в сам процесс поднятия (fail-fast, не полагаться на память)
- дамп загружен, в нём подтверждённо нет секретов (грепом, задокументированным в README стенда)
- скрипт прогона существует и запускается, даже если большинство ASSERT красные на старте
