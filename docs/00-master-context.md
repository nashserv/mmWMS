### 3.1 Почему остаток 92 единицы — разгадка

В боевом контейнере `fbs-workstation`: **`WORKSTATION_IGNORE_STOCK=true`**, `WORKSTATION_FULFILLMENT_MODE=true`.

Что это включает (`mmx_wms_bridge/models/bridge.py`):

```python
if reserved < task.quantity and not mismatched and self._ignore_stock():
    # Товар лежит на полке, а по учёту его нет. Дописываем строку сами:
    # склад соберёт вещь, а расхождение разберёт инвентаризация — на
    # сборке оно стоить смены не должно.
    self._force_reservation(move, source, destination, seller.owner_id, task.quantity)
    reserved, mismatched = task.quantity, False
```

Система **дописывает резерв на товар, которого нет по учёту**. Это не баг, а сознательный обходной клапан: книги врут, смену останавливать нельзя.

Отсюда 1231 quant и 92 единицы на 21 продавца. Учёт не ведётся, потому что от него намеренно не зависят.

**Что при этом молчит:** `_force_reservation` не оставляет ни записи о расхождении, ни события, ни задачи инвентаризации. Комментарий говорит «разберёт инвентаризация» — но инвентаризации никто не сообщает.

**Решение для новой WMS — раздел 6.5.**

### 3.2 Немаппленный товар — как есть

```python
if not seller:            return self._error("SELLER_MAPPING_MISSING")
# поиск: barcode → external_sku → barcode == sku, каждый с limit=2
if len(product_map) != 1: return self._error("PRODUCT_MAPPING_MISSING" | "AMBIGUOUS_PRODUCT_MAPPING")
```

Резерв не создаётся, возвращается код. Шлюз переводит в `MANUAL_REVIEW` **только** «WMS owner mismatch» и кривые метаданные WB — маппинга среди причин нет. Отсюда 3 задания в `MANUAL_REVIEW` на 6374, а `PRODUCT_MAPPING_MISSING` уходит в отказ и, вероятно, дальше в `CANCELLED` без причины — часть тех 2645.

**Два доменных правила отсюда, обязательны к переносу:**

1. У Wildberries поле называется `sku`, но приходит в нём **штрихкод**. Поиск в три шага: `barcode` → `external_sku` → `barcode == sku`.
2. Поиск с `limit=2`. Два совпадения — это `AMBIGUOUS`, а не «берём первое». У одной карточки несколько размеров; штрихкод определяет вещь на полке, артикул только модель.

### 3.3 Этикетка — почему не моментально

`WbGatewayLabelAdapter.label()` вызывается **в момент упаковки** и запускает цепочку:

```
клик → POST /sellers/{s}/wb/fbs/tasks/{id}/label
      → шлюз открывает накопительную поставку клиента     (вызов в WB)
      → кладёт заказ в поставку                            (вызов в WB)
      → запрашивает стикер                                 (вызов в WB)
      → PNG в base64, проверка SHA-256, до 10 МБ
      → агент печати → драйвер ОС → спулер
```

До трёх последовательных вызовов Wildberries, пока человек ждёт. Плюс формат: `WB_STICKER_FORMAT` по умолчанию **`png`** (`service.py:133`), хотя шлюз поддерживает `png | svg | zplv | zplh`.

Логика «стикер только для задания в поставке» — правильная, это требование WB. Но выполнять её можно в момент резерва, а не упаковки.

**Решение — раздел 6.6.**

## 4. Физический процесс склада

- Одновременно работают **5 сборщиков и 5 приёмщиков**. Десять параллельных писателей в остаток.
- Сборщик работает **за ПК**. Печатается **бумажный лист подбора** (PDF с фото, `picklist.py`). Идёт по складу с листом и **беспроводным сканером на поясе**, у стойки сканирует штрихкод коробки и штрихкод товара. Возвращается к ПК: упаковка, стикер, короб, поставка.
- **Принтер этикеток — на каждом рабочем месте.** Пять станций, пять принтеров. Очереди печати и арбитража не нужно, этикетки физически не смешиваются. Принтеры **USB** (не сетевые) — агент печати на ПК остаётся в цепочке, должен работать на пуше и постоянном соединении, а не на опросе.
- **ТСД нет и не нужен.** Офлайн-приложение не нужно — ПК на проводе.
- Ошибка, найденная у ПК после обхода, **приемлема** по решению владельца. Главный рубеж качества — контрольный скан при упаковке.
- Сессия подбора многопродавцовая (`PickSession` → `SellerStage` → `PickLine`): один обход собирает задания нескольких клиентов.
- Склад один, код `RUM`, Москва.

**Физическая пропускная способность:** 5 сборщиков дают 300–750 заданий в час. Система при этом проектируется с запасом до 10 000 в час (раздел 5, п. 4).

## 5. Решения владельца (зафиксированы, не обсуждаются)

1. **Уходим от Odoo.** Строим своё складское приложение под свои нужды.
2. **WMS сама работает с Wildberries.** Опрос заданий, резерв, остатки, стикеры, поставки — внутри WMS, одна база, одна транзакция. Никаких очередей между WB и складом.
3. **Только FBS** на первом круге. Без FBO, Ozon, логистики, отслеживания доставки.
4. **Запас пропускной способности — 10 000 заданий в час.** Это требование к системе, не план физической сборки. Штат, ТСД, волновой подбор не меняются.
5. **Публикация остатков в WB — немедленная.** Никаких таймеров и накопления. Ограничитель только как защита от бана Wildberries.
6. **Этикетка выходит моментально.** Цель — от нажатия до движения головки принтера менее 300 мс.
7. **Приоритеты:** (1) WMS — приёмка, хранение, отгрузка; (2) бесшовное приложение сборщика; (3) ЛК клиента; (4) ЛК админа; (5) ЛК работников.
8. Процесс склада — как в разделе 4. Не менять под систему; систему делать под процесс.
9. Модель денег — трёхуровневая наценочная (раздел 1). Дерево менеджеров с историей закреплений.
10. Строить на **отдельном сервере-стенде**. Боевой контур не трогать, только чтение.
11. **Начальный остаток при переключении клиента даёт владелец.** Инвентаризацию склада проектировать не нужно.
12. Работать **2–3 ИИ-агентами параллельно** по разбиению из раздела 9.
13. Стек — тот же, что в платформе (2.2).
14. Принтеры этикеток — **USB**, по одному на рабочее место (пять станций).

## 6. Цель: WMS, которая сама говорит с Wildberries

### 6.1 Главный принцип

**Событие — это уведомление, а не способ доставки.**

Задание лежит в базе WMS в тот момент, когда WMS опросила Wildberries. Рабочее место **само спрашивает** свои задания по HTTP и видит их, даже если RabbitMQ лежит, воркер умер, сообщение потерялось.

События остаются — биллингу, порталу, аналитике. Но склад от них не зависит.

Это архитектурно убивает «заказы иногда не падают в приложение»: между WB и заданием больше нет очереди.

### 6.2 Целевой путь заказа — одна транзакция

```
опрос WB (внутренний воркер wms, лизинг по аккаунту)
   ↓
BEGIN
  INSERT wms_task              ON CONFLICT (wb_order_id) DO NOTHING
  SELECT stock_balance ... FOR UPDATE
  INSERT reservation
  INSERT stock_move            (good → reserved)
  INSERT outbox                (wms.reservation.succeeded.v1)
COMMIT
   ↓
фоново, вне транзакции: положить в поставку + запросить стикер (ZPL)
   ↓
рабочее место опрашивает /tasks/pull → видит задание, стикер уже лежит
```

Postgres, 2–5 мс. Либо всё, либо ничего. Расхождение «заказ есть, резерва нет» становится **невозможным по построению**.

**Ни одного HTTP-вызова внутри транзакции.** Вызов WB на 500 мс внутри блокировки роняет пропускную способность на три порядка.

### 6.3 Что уходит с горячего пути

| Компонент | Судьба |
|---|---|
| `wb-fbs-gateway` | поглощается сервисом `wms` |
| `gateway-sync-worker` | внутренний опросчик `wms` |
| `gateway-command-worker` | **исчезает** — команд нет, есть транзакция |
| `catalog-stock-worker` | **исчезает** — `wms` публикует остатки сама |
| `workstation-inbox-consumer` | **уходит с критического пути** — рабочее место опрашивает `wms` |

Четыре очереди и три из четырёх молчащих воркеров уходят вместе с проблемой, которую создавали.

### 6.4 Публикация остатков — немедленно

Остаток изменился — вызов в WB уходит **сразу**. Таймеров нет, накопления нет.

Единственное следствие того, что HTTP занимает время: если для кабинета вызов уже в полёте, изменение уезжает следующим, который стартует в момент возврата текущего. Это конвейер, а не задержка. Если за время полёта изменилось несколько SKU — они уедут одним запросом (эндпоинт WB принимает пачку штрихкодов), что не медленнее и экономнее по лимиту.

**Ограничитель — только защита от бана.** Лимит Wildberries 300 запросов в минуту на кабинет. При реальных объёмах (около 2 заданий в минуту на все кабинеты) он не сработает никогда. Но массовая приёмка на 500 SKU выпустит 500 вызовов и получит блокировку кабинета — тогда очередь придерживается. В нормальной работе очередь пуста.

Формула публикации: `available = good − reserved − buffer(sku)`. Всегда занижать (инвариант 6).

### 6.5 Клапан «собрать без остатка» — сохранить, но сделать видимым

Убирать нельзя: в первый день новой WMS учёт где-то будет неверен, и если подбор встанет — операторы снова пойдут в обход, ровно та беда, которую чиним.

**Целевое поведение.** Товара по учёту не хватает, но резерв всё равно нужен:

1. резерв создаётся, движение пишется с `reason = 'ledger_short'`
2. в той же транзакции пишется `discrepancy(kind='ledger_short')` с владельцем, SKU, ячейкой, недостающим количеством
3. эмитится событие `wms.stock.shortfall.v1`
4. попадает на экран начальника склада и в счётчик Prometheus

Смена не встаёт. Ошибка становится видимой, счётной и адресной. Отключается флагом на уровне владельца товара, не глобально.

### 6.6 Этикетка моментально

**Стикер тянется заранее, не при упаковке.**

Задание зарезервировано → фоново, вне транзакции: положить заказ в накопительную поставку клиента, запросить стикер пачкой до 100 штук, сохранить у себя. К моменту нажатия «печать» этикетка уже локальна.

При 350 в день это 4 вызова к WB, при 10 000 в час — 100 вызовов. Побочная выгода: WB лёг — печать продолжается.

**Формат — ZPL, не PNG.** `WB_STICKER_FORMAT=zplv`. Шлюз уже поддерживает `png | svg | zplv | zplh`, сейчас стоит `png` по умолчанию. ZPL для этикетки 58×40 мм — 1–3 КБ текста против 20–100 КБ картинки, и принтер печатает его нативно, без растеризации драйвером. **Проверить на реальном принтере до принятия как факт** — см. раздел 13, вопрос 2.

**Печать — через агент на USB (раздел 4).** Агент держит постоянное соединение с `wms` (push, не опрос) и печатает RAW-байтами напрямую в устройство (`WritePrinter` с типом `"RAW"`, минуя графический драйвер).

```
клик «печать»
  → SELECT zpl FROM wb_label WHERE task_id = $1       1–3 мс
  → push агенту по открытому соединению                5–20 мс
  → RAW-печать в устройство                            5–20 мс
  → принтер двигает головку                          50–150 мс
  ────────────────────────────────────────────────
  итого: 100–200 мс
```

**Отмена задания после выдачи стикера:** заказ освобождается из поставки (`release_from_supply` в адаптере уже есть), локальный стикер помечается недействительным.

### 6.7 Что строим — сервис `wms`

**Интеграция с Wildberries:** аккаунты и токены, лимиты по аккаунту, опрос заданий с курсором и перекрытием, стикеры (заранее, ZPL), поставки, передача в доставку, публикация остатков, сверка статусов.

**Журнал остатков:** append-only движения, баланс как проекция, резервы под конкретное задание.

**Приёмка:** пересчёт, типизированные расхождения (недостача / излишек / пересорт / бой) с решением, размещение в коробки и ячейки. Пять приёмщиков параллельно.

**Хранение:** остаток по ключу `владелец × SKU × ячейка × коробка × состояние`; состояния товара; перемещения; инвентаризация частичная и полная.

**Отгрузка:** резерв → сессия подбора → скан у стойки → упаковка с контрольным сканом → печать стикера → короб → поставка → передача. Пять сессий параллельно.

**Коробки и адреса:** сохранить практику склада (2.9).

**Возвраты:** контрактные маршруты минимально — принять, решить.

**События:** полный набор `wms.*` и `inventory.*` через собственный outbox напрямую в RabbitMQ, с ретеншеном и партиционированием.

**Контракт `/api/mmx/wms/v1/*` сохраняется** для рабочего места и каталога — под него уже написаны клиенты. Плюс новые маршруты: `/tasks/pull`, экраны приёмки и размещения, управление кабинетами WB.

### 6.8 Что остаётся снаружи

`fbs-operator-workstation` (свой ритм, свои люди, свой релизный цикл), `billing`, `portal*`, `internal-admin`, `identity`, `notifications`, `analytics`.

**`product-catalog`** — сохраняет маппинг SKU ↔ карточки WB. Карточки Wildberries берёт **через `wms`**, не через отдельный шлюз. Снимки остатков из каталога уходят: `wms` публикует сама.

**`wb-returns`** — после вывода Odoo зовёт `wms` по тому же контракту `returns/*`. Правки адаптера — поток A вместе с контрактом.

### 6.9 Чего не строим

FBO, Ozon, карго и логистика (`mmx_logistics`), маркировка Честный Знак, отслеживание доставки, себестоимость и оценка запасов (товар чужой), мобильное и офлайн приложение, ТСД, волновой подбор, партионный учёт и сроки годности (см. раздел 13).

## 7. Целевая модель данных сервиса `wms`

База `wms` на том же Postgres. Схема замораживается потоком 0 до старта A/B/C.

```sql
-- === Справочники: владелец товара — первый класс ===
owner(id, seller_external_id UNIQUE, name, inn, active,
      allow_ledger_short BOOL DEFAULT true,           -- клапан 6.5, по владельцу
      created_at)
sku(id, owner_id, seller_sku, barcode, name, dims_mm, weight_g,
    buffer INT DEFAULT 0,                             -- страховой запас для публикации
    UNIQUE(owner_id, barcode))
warehouse(id, code UNIQUE)                            -- 'RUM'
zone(id, warehouse_id, code, kind)                    -- receiving|storage|picking|packing|shipping|quarantine|defect
cell(id, zone_id, address UNIQUE, capacity, route_order, active)   -- route_order = маршрут обхода
box(id, barcode UNIQUE, owner_id, sku_id, cell_id, quantity, counted BOOL,
    comment NOT NULL, sequence, total_boxes, state, created_by, created_at)

-- === Рабочие места и принтеры ===
station(id, name, printer_host, printer_port DEFAULT 9100,
        printer_model, transport, active)             -- transport: 'tcp' | 'agent' (сейчас 'agent' — USB)

-- === Интеграция с Wildberries ===
wb_account(id, owner_id, external_id UNIQUE, display_name, secret_ref, scopes,
           mode, status, token_type, token_expires_at, last_verified_at,
           last_sync_at, next_sync_at, sync_claimed_at, sync_attempts, sync_error_code,
           wb_warehouse_id)
wb_sync_cursor(account_id, cursor, last_seen_at)
wb_rate_limit(account_id, window_start, used, blocked_until)
wb_supply(id, wb_account_id, wb_supply_id, state, closed_at)
wb_label(id, task_id UNIQUE, format, payload, checksum, version,
         fetched_at, invalidated_at)                  -- ZPL лежит локально
wb_stock_push(id, account_id, pushed_at, rows, result)

-- === Журнал — единственный источник истины ===
stock_move(id, ts, owner_id, sku_id,
           cell_from, cell_to, box_from, box_to,
           state_from, state_to, qty,
           reason, doc_type, doc_ref, actor_id,
           idem_key UNIQUE)                           -- append-only; триггер запрещает UPDATE/DELETE
stock_balance(owner_id, sku_id, cell_id, box_id, state, qty,
              PRIMARY KEY(owner_id, sku_id, cell_id, box_id, state))

-- === Резерв ===
reservation(id, task_id, owner_id, sku_id, cell_id, box_id, qty,
            state, expires_at, created_at, released_at, release_reason)

-- === Задание ===
wms_task(id, wb_order_id UNIQUE, wb_order_uid, wb_account_id, owner_id, sku_id,
         barcode, quantity, deadline, state, wb_status, reservation_id,
         label_id, package_ref, supply_id,
         assignee, claimed_at, claim_expires_at,      -- выдача сборщику
         cancel_reason,                               -- NOT NULL при state='cancelled'
         manual_review_code, manual_review_reason,    -- код из 3.2
         last_reconciled_at, created_at, updated_at, version)

-- === Приёмка ===
receipt(id, owner_id, reference UNIQUE, warehouse_id, state, actor_id, created_at)
receipt_line(id, receipt_id, sku_id, expected_qty, actual_qty, box_id, cell_id)
discrepancy(id, receipt_id, task_id, owner_id, sku_id, kind, qty,
            decision, liable, comment, actor_id, created_at)
   -- kind: shortage | surplus | mismatch | damage | ledger_short

-- === Инвентаризация ===
inventory_count(id, owner_id, reference UNIQUE, scope, state, actor_id, created_at, applied_at)
inventory_count_line(id, count_id, sku_id, cell_id, box_id, expected_qty, fact_qty)

-- === Подбор и отгрузка ===
pick_session(id, actor_id, station_id, state, started_at, finished_at,
             picklist_barcode UNIQUE)
pick_line(id, session_id, task_id, owner_id, sku_id, cell_id, box_id, qty,
          scanned_at, scan_result)
shipment(id, owner_id, wb_supply_id, state, closed_at)

-- === Возвраты ===
wms_return(id, task_id, return_event_id UNIQUE, owner_id, state, decision, reason, received_at)

-- === События ===
outbox(id, event_id UUID UNIQUE, type, tenant_id, occurred_at, payload JSONB,
       correlation_id, sequence, published_at, attempts, last_error)
       -- партиционирование по дате, ретеншен опубликованного
```

**Состояния товара** (`state`): `good`, `reserved`, `quarantine`, `defect`, `blocked`, `processing`. Обязательны на первом круге `good`, `reserved`, `defect`; остальные в схеме с первого дня.

**Автомат задания** (`wms_task.state`):

```
new → reserved → picking → picked → packed → labeled → in_supply → shipped
                    ↓
                  short ──→ cancelled       (недостача; причина обязательна)
       любое → manual_review                (немаппленный/неоднозначный товар, кривые метаданные WB)
       любое → diverged                     (наш статус ≠ статус WB; будит человека)
```

**Выдача заданий сборщикам** — пять параллельных сессий, задание не должно уйти двоим:

```sql
SELECT ... FROM wms_task
 WHERE state = 'reserved' AND assignee IS NULL
 ORDER BY deadline                          -- срок WB, не время создания
 FOR UPDATE SKIP LOCKED
 LIMIT $n
```

Плюс лизинг: `claim_expires_at`, задание освобождается, если сборщик пропал.

Маппинг `wms_task.state` ↔ статусы рабочего места (`queued/picking/picked/printed/packed/boxed/shipped/closed/cancelled`) ↔ канонические ↔ WB — фиксируется потоком 0 отдельной таблицей.

## 8. Инварианты — правила, которые нельзя нарушать

1. **Заказ и резерв создаются одной транзакцией.** Никогда двумя сервисами, никогда через очередь. Нет товара — та же транзакция пишет `short` либо `ledger_short` с расхождением.
2. **Ни одного HTTP-вызова внутри транзакции.** Транзакция — только Postgres, миллисекунды. WB-вызовы до и после, асинхронно.
3. **`stock_balance` меняется только проекцией из `stock_move`.** Прямых `UPDATE`/`INSERT` в баланс нет нигде. `stock_move` append-only, триггер запрещает `UPDATE`/`DELETE`.
4. **Резерв берёт `SELECT … FOR UPDATE`** по ключу `(owner, sku, cell, box)`. Выдача заданий сборщику — `FOR UPDATE SKIP LOCKED`. Время удержания блокировки под 100 мс, измеряется.
5. **Каждая команда идемпотентна** по внешнему ключу (`wb_order_id`, `idem_key`, `reference`, `return_event_id`). Повтор — тот же ответ, не второе движение.
6. **Изоляция владельца.** Резерв, скан, отгрузка, инвентаризация не пересекают `owner_id`. Товар без маппинга — `manual_review` с кодом, не остаток.
7. **В WB публикуется заниженный остаток немедленно:** `available = good − reserved − buffer(sku)`, вызов уходит сразу, без таймеров.
8. **Задание доступно рабочему месту сразу после записи в базу**, без публикации события.
9. **Стикер лежит локально до того, как человек нажал печать.** Формат ZPL (проверить на реальном принтере — раздел 13, вопрос 2). Запрос к WB в момент упаковки запрещён.
10. **Расхождение с WB — состояние `diverged` и алерт**, а не тихая запись.
11. **Причина отмены обязательна** на уровне схемы.
12. **Сборка без остатка оставляет след:** `discrepancy(kind='ledger_short')`, событие, счётчик. Молчаливого `_force_reservation` больше нет.
13. **Физическое действие = движение + событие + начисление.**
14. **Молчащий воркер считается сломанным.** Метрика «обработано за минуту» и алерт на ноль.
15. **Токены WB и любые секреты** не попадают в события, логи, ответы API, тесты и фикстуры.

## 9. Разбиение работы

Полное разбиение — в четырёх отдельных файлах, каждый самодостаточен поверх этого мастер-контекста:

- **`01-stream-0-contracts-and-stand.md`** — поток 0: контракты, схема, стенд. Один исполнитель, 2–3 дня, до старта остальных.
- **`02-stream-a-wms-wildberries.md`** — поток A: сервис `wms`, интеграция с Wildberries, журнал остатков. 4–5 недель.
- **`03-stream-b-picker-app.md`** — поток B: приложение сборщика и приёмщика, лист подбора, печать. 2–3 недели.
- **`04-stream-c-billing-accounts.md`** — поток C: тарифы, партнёры, онбординг, ЛК. 3 недели.

Ниже — то, что действует **на все четыре потока одинаково**: правила параллельной работы, проверки полного прогона, сроки.

### 9.5 Правила параллельной работы

1. **Один агент — один каталог.** Чужие файлы не редактируются. Нужно чужое — заявка в поток 0.
2. **Контракт после заморозки меняется только потоком 0** с одновременным обновлением всех троих.
3. **Тесты пишутся против контракта**, не против чужого кода.
4. **Зависимости через mock** до готовности. Никто никого не ждёт.
5. **Ежедневный полный прогон на стенде.** Красный — чинит тот, чей контракт нарушен.
6. **Один интегратор с правом мержа.** Ветки `stream-a`, `stream-b`, `stream-c`, PR в `main` мержит только интегратор.
7. **Каждый поток заканчивается критерием, не датой.**

Для всех: коммиты небольшие, сообщение — что изменилось для склада; секреты только из env и секрет-провайдера, паттерн `${VAR:?set outside Git}` обязателен; существующие миграции не переписываются; комментарии в коде по-русски, объясняют «зачем», а не «что».

### 9.6 Скрипт полного прогона — что именно проверяет

Гоняется ежедневно, красный блокирует мерж. Владелец каждого шага указан в скобках — стрим, который чинит красный.

```
1.  Завести клиента, ячейки, загрузить начальный остаток            (C, A)
    ASSERT stock_balance == загруженному, stock_move содержит doc_type='opening'
2.  Приёмка 3 SKU в коробки и ячейки                                 (A, B)
    ASSERT баланс вырос ровно на принятое; каждая коробка имеет непустой comment
3.  Приёмка с недостачей                                             (A, B)
    ASSERT discrepancy(kind='shortage') создан, баланс по факту, не по ожиданию
4.  Симулятор WB отдаёт 5 заданий                                    (A)
    ASSERT 5 wms_task за < 2 с; 5 reservation; баланс good упал, reserved вырос
    ASSERT ни одного HTTP-вызова внутри транзакции (проверка по трейсу)
5.  Задание на немаппленный товар                                    (A)
    ASSERT state='manual_review', manual_review_code='PRODUCT_MAPPING_MISSING',
           резерв не создан
6.  Задание на товар с нулевым остатком, allow_ledger_short=true     (A)
    ASSERT резерв создан, discrepancy(kind='ledger_short'), событие
           wms.stock.shortfall.v1
7.  Стикеры                                                          (A)
    ASSERT wb_label заполнен для всех 5 заданий ДО начала подбора, format='zplv'
8.  Пять параллельных сессий подбора тянут задания                   (A, B)
    ASSERT ни одно задание не выдано двоим, ни одно не потеряно
9.  Подбор, скан у стойки, упаковка с контрольным сканом             (B)
```

## 11. Миграция и переключение

Заменяется не только Odoo, но и шлюз WB. Поэтому осторожнее.

**Шаг 1 — стенд.** Полный прогон 9.6 зелёный с настоящим `wms` и симулятором WB.

**Шаг 2 — shadow на проде, только чтение.** `wms` развёрнута рядом, опрашивает WB **исключительно `GET /api/v3/orders`**. Ни одной записи: ни стикеров, ни поставок, ни публикации остатков. Строит свою таблицу заданий, ежедневный отчёт расхождений. Минимум неделя.

> **Лимиты WB при shadow.** Два опросчика бьют в один кабинет, лимит 300 запросов в минуту общий. Опрос `wms` в shadow ставится реже боевого либо бюджет делится явно. Упереться в лимит на проде из-за теневого опроса недопустимо.

**Шаг 3 — один клиент, начальный остаток.** Владелец даёт остаток по клиенту, загружаем через админку, движения пишутся с `doc_type='opening'`.

**Шаг 4 — один клиент, публикация остатков.** Для него остатки в WB публикует `wms`. Первая запись в WB, обратима за минуту.

**Шаг 5 — один клиент, полный цикл.** Задания, резерв, стикеры, поставки. Боевой шлюз для него отключается. Неделя наблюдения.

**Шаг 6 — все.** По одному кабинету, не пачкой.

**Откат** на любом шаге: вернуть кабинет боевому шлюзу. `wms` продолжает в shadow. Данные обратно не мигрируются — боевой контур всё время оставался актуальным.

**Odoo** отключается после шага 6, остаётся read-only, не удаляется. Судьба `mmx_logistics` — отдельное решение владельца.

**Никакой деплой, push или изменение боевого контура без явного разрешения владельца.**

## 12. Безопасность и границы

- **На стенде нет живых токенов WB.** Ни одного. `wb_account_secrets` в дампе — заглушки, работа только через `wb-simulator`. Живой токен на стенде отправит настоящие команды в кабинет клиента: создаст поставку, переведёт задание в собранное, перезапишет остатки. Необратимо, и узнает об этом клиент, а не мы. Проверка отсутствия живых токенов — первый шаг любого запуска стенда.
- **`wms` становится держателем токенов WB.** Зона доверия расширяется на складской сервис. Токены только через секрет-провайдер, в базе `wms` — ссылка `secret_ref`, не значение; в события, логи, ответы API, тесты не попадают; управление аккаунтами — отдельная роль.
- **Радиус отказа.** Опрос WB — отдельный воркер с изоляцией: упал опрос, приёмка, подбор и инвентаризация продолжают работать.
- Боевой сервер `91.108.239.175` — **только чтение** до отдельного разрешения владельца на каждое изменение.
- Секреты — только env-файлы вне Git и секрет-провайдер, паттерн `${VAR:?set outside Git}`.
- `identity` — единственный источник пользователей и ролей; `wms` доверяет JWT по JWKS.
- У `185.73.126.232` сменился SSH host key (`SHA256:GvT7LJukuWb3BXYspO8e4z7+hzNR6i8lJLblEz4lr7g`). До подтверждения владельцем, что сервер переустанавливался, не подключаться.
- **Стенд** — сервер `151.245.140.225`, доступ только по SSH-ключу, пароль root отключён. Живых токенов WB на нём быть не должно — проверяется первым делом при разворачивании (см. поток 0).

## Приложение C — Формы ключевых запросов

**Резерв** (`/reservations`):
```json
{"request_id", "idempotency_key", "gateway_order_id", "seller_external_id",
 "wb_account_external_id", "wb_order_id", "order_uid", "sku", "barcode",
 "quantity", "deadline", "correlation_id"}
```
Ответ: `{"status": "reserved" | ..., "task_id", "owner_external_id", "error_code"}`. Клиент считает принятым при `status == "reserved"`.

**Коды ошибок резерва (сохранить все):** `SELLER_MAPPING_MISSING`, `PRODUCT_MAPPING_MISSING`, `AMBIGUOUS_PRODUCT_MAPPING`, `WAREHOUSE_UNKNOWN`, `INSUFFICIENT_STOCK`, `SERIALIZATION_RETRY`.

**Остатки** (`/catalog/stocks/bulk`): запрос `{"seller_external_id"}`, ответ `{"stocks": [{"barcode", "available": int ≥ 0}]}`. Строки без штрихкода или с нецелым/отрицательным `available` отбрасываются.

**Приёмка** (`/receipts`):
```json
{"seller_external_id", "warehouse_code": "RUM", "reference",
 "lines": [...], "seller_name", "seller_inn"}
```
Владельца, которого склад видит впервые, заводит по `seller_name`/`seller_inn`.

**Инвентаризация** (`/inventory/count`): `{"seller_external_id", "warehouse_code", "reference", "scope": "partial"|"full", "lines": [...]}`

**Скан** (`/tasks/{id}/scan`): запрос `{"barcode"}`, ответ `{"status": "picked", "owner_external_id", ...}`. Клиент принимает только если `owner_external_id` совпал и `status == "picked"`. При потере ответа повторно читает задание и принимает, если оно уже `picked` с тем же штрихкодом.

**Этикетка** (`/tasks/{id}/label`): ответ `{"id", "order_id", "version" (1..2147483647), "payload" (≤10 МБ), "content_type", "checksum" (sha256 от payload), "sticker"}`. Контрольная сумма проверяется `hmac.compare_digest`. `order_id` обязан совпасть с заданием.

**Возврат** (`/tasks/{id}/return`): `{"return_event_id", "seller_external_id", "reason"}` → `{"return_id"}`.

**Отмена** (`/tasks/{id}/cancel`): `{"cancellation_event_id", "handed_over": bool}`.

## Приложение E — Схемы payload событий

Извлечено из `services/wb-fbs-gateway/contracts/asyncapi.yaml`. Все события обёрнуты в `EventEnvelope`.

**EventEnvelope** — `additionalProperties: false`, обязательны: `event_id` (uuid), `tenant_id` (1–128), `type`, `occurred_at` (date-time), `payload` (object), `correlation_id`.

**TaskPayload** (`wb.fbs.order.synced.v1`, `wb.fbs.order.updated.v1`): обязателен `task` → `TaskProjection`.

**InventoryMovementPayload** (`inventory.movement.recorded.v1`) — `additionalProperties: false`, обязательны:
```
movement_type : WmsEventType (одно из имён wms.*)
sku           : string, minLength 1
quantity      : number
order_id      : integer
status        : TaskStatus
occurred_at   : date-time
reference     : string | number   (опционально)
```

**SupplyShippedPayload** (`wb.supply.shipped.v1`) — обязательны:
```
supply      : string   — идентификатор поставки WB (WB-GI-…)
seller_id   : string   — организация клиента, кому выставляется счёт
orders      : integer ≥ 0 — заказов в поставке, тарифицируемое количество
accepted_at : date-time | null — когда WB отсканировал QR поставки (scanDt)
name        : string
```

**ReturnDetectedPayload** (`wb.fbs.return.detected.v1`) — обязательны:
```
return_id : string, pattern ^wb-[0-9a-f-]{36}$
task_id   : string, uuid
```

**Порядок событий по заданию.** В Odoo-аутбоксе на каждое задание ведётся `sequence`: инкремент под блокировкой строки задания, событие и номер пишутся атомарно. Потребители полагаются на монотонность в пределах задания. **В новой WMS сохранить**: `outbox.sequence` инкрементируется в той же транзакции, что и движение.

**Список `WMS_EVENT_TYPES`** (валидируется при эмиссии): `wms.reservation.succeeded.v1`, `wms.reservation.failed.v1`, `wms.picking.started.v1`, `wms.item.scanned.v1`, `wms.picking.completed.v1`, `wms.packing.completed.v1`, `wms.label.attached.v1`, `wms.returned.to.shelf.v1`, `wms.return.expected.v1`, `wms.return.received.v1`, `wms.return.resellable.v1`, `wms.return.defective.v1`, `wms.order.cancelled.v1`.
