# Маппинг статусов — заморожено потоком 0

Единая таблица, на которую ссылаются потоки A, B и C. Меняется только потоком 0
с одновременным обновлением всех трёх (правило 9.5.2 мастер-контекста).

Источники: раздел 7 мастера (автомат задания), раздел 2.12 (маппинг WB),
раздел 3 (состояния рабочего места в боевом контуре), приложение A.

---

## 1. Основная таблица

Читается слева направо: одно состояние задания в `wms` даёт ровно один статус
в каждой из трёх остальных систем. Пустых ячеек нет.

| `wms_task.state` | Статус рабочего места | Канонический статус | Статус WB |
|---|---|---|---|
| `new` | `queued` | `RECEIVED` | `new` |
| `manual_review` | `queued` | `MANUAL_REVIEW` | `new` |
| `short` | `queued` | `RESERVATION_FAILED` | `new` |
| `reserved` | `queued` | `RESERVED` | `new` |
| `picking` | `picking` | `PICKING` | `new` |
| `picked` | `picked` | `PICKED` | `new` |
| `packed` | `packed` | `PACKED` | `new` |
| `labeled` | `printed` | `LABEL_READY` | `new` |
| `in_supply` | `boxed` | `SUPPLY_ASSIGNED` | `confirm` |
| `shipped` | `shipped` | `OUT_FOR_DELIVERY` | `complete` |
| `handed` | `closed` | `HANDED_TO_WB` | `complete` |
| `accepted` | `closed` | `ACCEPTED_BY_WB` | `complete` |
| `cancelled` | `cancelled` | `CANCELLED` | `cancel` |
| `diverged` | последний известный до расхождения | последний известный до расхождения | любой, отличный от нашего — в этом и суть состояния |

### Поправка: `confirm` законен и до `in_supply`

Столбец «Статус WB» выше читается как «что WB покажет, когда у нас именно это
состояние». У состояний подбора — `reserved`, `picking`, `picked`, `packed`,
`labeled` — там стоит `new`, и это верно ровно до того момента, пока заказ не
положен в поставку.

Но стикер Wildberries выдаёт **только** заданию, уже лежащему в поставке, а
стикеры берутся заранее, пачкой, задолго до подбора (инвариант 9, раздел 6.6).
Значит `wms` кладёт заказ в накопительную поставку сразу после резерва — и с
этой секунды WB отвечает `confirm`, хотя у нас ещё `reserved`.

Поэтому сверка допускает `confirm` для состояний подбора **при непустом
`wms_task.supply_id`**, и только при нём:

| `wms_task.state` | `supply_id` | Статус WB `confirm` |
|---|---|---|
| `reserved`, `picking`, `picked`, `packed`, `labeled` | пуст | расхождение |
| `reserved`, `picking`, `picked`, `packed`, `labeled` | заполнен | согласуется |
| `in_supply` | любой | согласуется (строка таблицы 1) |

Без этой поправки каждое живое задание уходило в `diverged` в течение минуты:
сверка отменяла работу стикеровщика, а склад получал остановленные задания на
ровном месте. Код — `IN_SUPPLY_TOLERATES_CONFIRM` и аргумент `in_supply`
функции `agrees_with_wb` (`services/wms/app/domain.py`).

Обратное направление правило не меняет: `confirm` у задания, которого нет в
поставке, остаётся расхождением. Именно оно значит «кто-то положил наш заказ в
чужую поставку».

### Три состояния, которые легко перепутать

`shipped`, `handed` и `accepted` — это три разных факта, и различать их
обязательно (раздел 2.12):

- `shipped` — мы вызвали у WB передачу поставки. WB отвечает `complete`.
  **Это не доказательство приёмки.** В боевом контуре 6072 задания висят в
  `complete`, и именно на этом строилась иллюзия, что всё доехало.
- `handed` — **человек подтвердил** физическую передачу. Подтверждение
  записывается на поставке (`shipment.handed_by`, `shipment.handed_at`),
  схема не даёт перевести поставку в это состояние без подписи.
- `accepted` — **сверка с WB** подтвердила приёмку. Терминальный успех.
  Только сверка, никогда не вывод из `complete`.

Сегодня `HANDED_TO_WB` подтверждён меньше чем у 1 % отгруженных; цель — 95 %
(раздел 10).

## 2. Обратное направление: статус WB → состояние задания

Так работает опросчик. Правила из раздела 2.12 мастера.

| Статус WB | Состояние в `wms` | Правило |
|---|---|---|
| `new` | `new` → сразу `reserved` в той же транзакции | Валидировать, зарезервировать с учётом владельца (раздел 6.2) |
| `confirm` | `in_supply` | Задание прикреплено к поставке |
| `complete` | `shipped` | Поставка передана. Дальше `handed`/`accepted` только по подтверждению и сверке |
| `cancel` | `cancelled`, если физически не обработано; иначе разбор возврата | `cancel_reason` обязателен на уровне схемы (инвариант 11) |

Строка `cancel` — **команда, а не расхождение**. Сверка отменяет задание сама,
если оно в одном из состояний `new`, `reserved`, `short`, `manual_review`,
`picking`, `picked` (`CANCELLABLE_ON_WB_CANCEL`): резерв снимается, товар
возвращается в `good`, причина пишется разбираемой — «отменено у Wildberries
(заказ N)». Из `packed`, `labeled`, `in_supply`, `shipped`, `handed`,
`accepted` отмены нет: товар уже в коробе или уехал, и это разбор возврата
(раздел 2.12), который делает человек.

В боевом контуре 2645 отмен лежали с пустой причиной, а товар оставался в
резерве под заказ, которого больше нет.

**Если статус WB не соответствует нашему** по этой таблице — задание уходит в
`diverged` и поднимается алерт (инвариант 10), а не тихо перезаписывается.
В боевом контуре таких расхождений 2467 из 6374, и все они молчали.

## 3. Канонические статусы, которые новая WMS не производит

Перечислены, чтобы никто из трёх потоков не искал их в схеме и не считал
пропуском. Каждый — следствие решения из мастера, а не забывчивости.

| Канонический статус | Почему не используется |
|---|---|
| `RESERVATION_REQUESTED` | Команд на резерв больше нет. Резерв происходит в той же транзакции, что и создание задания (раздел 6.2), просить его не у кого |
| `PACKING` | Упаковка в новом процессе атомарна: контрольный скан и упаковка — один шаг (раздел 4). Отдельное «упаковывается» нечем наполнить |
| `LABEL_PENDING` | Стикер тянется заранее и уже лежит локально к моменту упаковки (инвариант 9). Ожидания стикера не существует |
| `READY_FOR_DELIVERY` | Дублирует `SUPPLY_ASSIGNED`. Раздел 2.12 закрепляет за `confirm` именно `SUPPLY_ASSIGNED` |
| `IN_DELIVERY_BATCH` | Отслеживание доставки вне скоупа (раздел 6.9) |
| `DELIVERY_FAILED` | То же — отслеживание доставки вне скоупа |
| `RESHIPMENT_REQUIRED` | То же |
| `RETURN_REQUESTED` | Возвраты ведутся отдельной сущностью `wms_return` со своим автоматом, а не состоянием задания (раздел 6.7) |
| `RETURNED_TO_WMS` | То же — см. таблицу 4 |

## 4. Автомат возврата

Возвраты на первом круге — контрактные маршруты минимально (раздел 6.7),
поэтому у них свой короткий автомат, отдельный от задания.

| `wms_return.state` | `wms_return.decision` | Событие | Канонический статус |
|---|---|---|---|
| `expected` | не заполнено | `wms.return.expected.v1` | `RETURN_REQUESTED` |
| `received` | не заполнено | `wms.return.received.v1` | `RETURNED_TO_WMS` |
| `decided` | `resellable` | `wms.return.resellable.v1` | `RETURNED_TO_WMS` |
| `decided` | `defective` | `wms.return.defective.v1` | `RETURNED_TO_WMS` |

## 5. Состояния товара — отдельная ось

Не путать с состоянием задания. Это состояние **вещи на полке**
(`stock_move.state_from` / `state_to`, `stock_balance.state`), домен
`wms_stock_state`.

| Состояние | Смысл | Первый круг |
|---|---|---|
| `good` | Годный, доступен к резерву | обязательно |
| `reserved` | Зарезервирован под конкретное задание | обязательно |
| `defect` | Бой, к отгрузке не годен | обязательно |
| `quarantine` | Спорный, до решения по расхождению | в схеме, не используется |
| `blocked` | Заблокирован решением | в схеме, не используется |
| `processing` | В обработке между операциями | в схеме, не используется |

В WB публикуется `available = good − buffer(sku)` (инвариант 7). Резерв не вычитается: движение `good → reserved` уже вывело его из `good`.
Остальные состояния в публикацию не входят никогда — всегда занижать.
