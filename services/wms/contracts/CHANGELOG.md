# Изменения контракта `wms`

Версия одна на оба файла — `openapi.yaml` и `asyncapi.yaml`: клиенту важно, с
какой версией сервиса он говорит, а не какой из двух документов поменялся.

Правки контракта — право потока 0 (правило 9.5.6 мастер-контекста), и каждая
записывается здесь и в `docs/schema-decisions.md`.

---

## 1.4.0 — 12.09.2026. Хранение считается от объёма товара

Обратная совместимость полная: добавлены два маршрута и колонка, ничего не
удалено и не переименовано. Клиент версии 1.0.0 продолжает работать.

Решение владельца 12.09.2026 (раздел 13): хранение тарифицируется по объёму
товара, а не по числу занятых коробов. Единица тарифа прежняя — коробо-место ×
сутки, — но количество вычисляется:

    коробо-места = Σ по штрихкодам ( остаток / units_per_box )

Норма снимается с приёмки: сколько этой вещи реально легло в короб. Габариты
для этого не нужны и не используются — их у нас нет ни одного (`dims_mm` пуст,
в карточке Wildberries габаритов тоже нет).

### Добавлено

- **`POST /storage/places`** — сколько коробо-мест занимал товар клиента на
  конец суток. `day` обязателен: остаток берётся из журнала на конец этих
  суток. Товар без нормы в `places` не входит и возвращается отдельно.
- **`POST /catalog/units-per-box`** — правка нормы руками. Норма, снятая с
  пробной партии в десять штук, завышает счёт вчетверо; правка — часть модели,
  а не административная роскошь.
- **`sku.units_per_box`** (миграция 010) — норма, максимум наблюдённого.
  `NULL` — нормы ещё нет.

### Изменено на стороне биллинга (контракта не касается)

`box_places` перестал считать различные штрихкоды коробов и спрашивает склад
про день. До этого досчёт за три дня трижды брал СЕГОДНЯШНИЙ остаток, то есть
начислял хранение за дни, когда товара ещё не было.

## 1.3.0 — 11.09.2026. Этап 2 аудита: ядро wms

Обратная совместимость полная: добавлены необязательное поле и два кода
отказа, ничего не удалено и не переименовано. Клиент версии 1.0.0 продолжает
работать без изменений.

### Добавлено

- **`TaskCancelParams.reason`** (`POST /tasks/{taskId}/cancel`) — готовая
  причина отмены, необязательная. Не передали — сервер выводит её сам, как и
  раньше.

  Зачем: сверка с Wildberries отменяет задания сама, и её причина разбираема —
  «отменено у Wildberries (заказ 900000123)». Выведенная «отменено по событию
  wb-cancel-900000123» — нет. Инвариант 11 требует непустую причину, а не
  именно выведенную сервером.

- **`ReservationErrorCode.OWNER_INACTIVE`** — клиент отключён. Раньше такой
  заказ получал `SELLER_MAPPING_MISSING` и отвергался без задания: заказ у
  Wildberries при этом существует, срок по нему идёт, и молчаливый отказ раз в
  две секунды не помогал никому. Теперь заводится задание в `manual_review` с
  этим кодом.

- **`ReservationErrorCode.UNPROCESSABLE_ORDER`** — заказ Wildberries не
  разобран: битая дата, дикое количество, чужое поле. Один такой ронял весь
  такт опроса кабинета; теперь он уходит в `manual_review`, а опрос идёт
  дальше.

- **`LabelPrintResult.order_id`** — номер заказа Wildberries, на который
  выписан стикер. Рабочее место сверяет его с заказом задания перед печатью:
  напечатанный чужой стикер отправит вещь другому покупателю, а сверять было
  нечем.

### Каталог событий

- **`wms.stock.released.v1` теперь издаётся.** Канал лежал в каталоге с
  первого дня, и издавать его было некому: потребитель узнавал об
  освобождённом товаре только из следующего движения по нему.

- **`wb.orders.processed.v1` больше не объявлен издаваемым.** Канал и форма
  сообщения остаются (имя унаследованное, его знают потребители боевого
  контура), но операции `send` у него нет: `wms` не издаёт это событие нигде.
  Физический факт, который оно описывало, издаётся как `wb.supply.shipped.v1`
  и тарифицируется по тому же полю `orders` — две строки на один факт означают
  два счёта клиенту за одну машину. Решение и его причина —
  `docs/stream-c-requests.md`, пункт 3.

### Изменено в поведении (форма запроса и ответа та же)

- **`POST /tasks/{taskId}/return-to-shelf` больше не снимает резерв.** Вещь
  физически осталась на той же полке и по-прежнему нужна этому заказу.
  Раньше резерв снимался, задание возвращалось в очередь без брони, и один и
  тот же товар уезжал по двум заказам.

- **`POST /shipments` c `action: "reconcile"`** подтверждает приёмку только по
  фактическому `complete` у Wildberries по каждому заказу поставки. Не
  подтвердил — отказ; задания остаются в `handed`. Раньше команда ставила
  `accepted` сама себе.

- **`POST /shipments` c `action: "hand_over"`** работает только по уехавшей
  поставке (`deliver` состоялся). Раньше человек мог подтвердить передачу
  машины, которую ещё не собрали.

- **`POST /tasks/pull`**: `states` — белый список `{reserved, picking}`.
  Запрос с другими состояниями отвергается. Раньше `states: ["shipped"]`
  выдавало сборщику задание, товар которого уже уехал.

- **Повтор команды с тем же `idempotency_key`** возвращает сохранённый ответ с
  `duplicate: true`, а не делает работу второй раз. Раньше ключ только
  проверялся на непустоту.

- **Внутренний сбой** отдаёт `request_id` вместо текста исключения. В тексте
  бывает фрагмент SQL и значения параметров.

- **`error.message` при отказе по клиенту с несколькими кабинетами**: команды
  поставки и каталога требуют явный `wb_account_external_id`. Раньше брался
  первый кабинет из списка, и ответ зависел от порядка строк в базе.

## 1.0.0 — исходный контракт потока 0

Перенос контракта `mmx_wms_bridge` на сервис `wms` плюс шесть новых маршрутов
(разделы 6.6, 6.7 мастера). Формы существующих маршрутов сохранены дословно:
под них уже написаны клиенты.
