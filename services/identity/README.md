# identity — роли

Поток C владеет **только ролями** сервиса `identity` и не трогает механику
JWT/JWKS (файл [`docs/04-stream-c-billing-accounts.md`](../../docs/04-stream-c-billing-accounts.md),
раздел «Владеет»).

## Граница этого каталога

Боевой `identity` существует на платформе и живёт в боевом контуре
(`/root/MM-express-final-platform-integration`). Его исходников в этом
репозитории нет, и выдумывать их описание значило бы записать в стенд неправду
(README стенда, раздел «Сервисы платформы»).

Поэтому здесь:

| Есть | Нет и не будет от потока C |
|---|---|
| справочник ролей | выпуск токенов |
| выдача роли с областью действия и отзыв с историей | подпись, JWKS, ротация ключей |
| `introspect` — делегирование боевому identity | вторая реализация проверки подписи |

Миграция строго **дополняющая**: свои таблицы с префиксом `identity_`, ни одной
правки в чужие, `CREATE TABLE IF NOT EXISTS`. Когда исходники приедут, она
накатывается на ту же базу поверх.

## Роли

Четыре существовали (раздел 2.11 мастера), четыре складские добавлены (файл 04),
две партнёрские нужны дереву менеджеров:

| Код | Кто |
|---|---|
| `owner`, `manager` | клиент: владелец организации и его сотрудник |
| `admin`, `accountant` | MM-Express: справочники и деньги |
| `warehouse_head`, `picker`, `receiver`, `logist` | склад |
| `senior_manager`, `account_manager` | продажи: партнёр и менеджер кабинетов |

## Область действия

`global`, `organization`, `seller` были и раньше. Новое — **`partner_branch`**:
областью становится узел дерева менеджеров. Отсюда и работает правило файла 04
«менеджер видит только своих клиентов и свою комиссию, старший — свою ветку
целиком»: ветка раскрывается рекурсивно в биллинге (`partner_subtree`), а
отдельной роли «старший» для этого не нужно — нужно лишь, чтобы под ним
кто-то был.

Какие именно кабинеты стоят за веткой, `identity` не знает и знать не должен:
дерево партнёров живёт в биллинге, здесь только «кто этот человек и что ему
можно».

## Проверка токена на стенде

Боевого `identity` на стенде нет, значит нет и настоящих токенов. `introspect`
принимает непрозрачный `stand:<uuid пользователя>` — и **отказывает вне
локальных сред**: заглушка, молча доехавшая до прода, это открытая дверь,
поэтому она закрыта проверкой окружения, а не памятью.

```bash
curl -s -X POST http://127.0.0.1:8084/api/identity/v1/introspect \
  -H 'Content-Type: application/json' \
  -d '{"token":"stand:<uuid>"}'
```

Когда боевой `identity` появится на стенде, ему задаётся `IDENTITY_UPSTREAM_URL`,
и проверка подписи уходит к нему целиком. Роли остаются здесь: боевой сервис о
четырёх складских ещё не знает.

## Запуск и тесты

Поднимается вместе с наложением потока C
(`infrastructure/stand/compose.stream-c.yaml`), порт `127.0.0.1:8084`.

```bash
cd services/identity
APP_ENV=test IDENTITY_TEST_DATABASE_URL=postgresql://wms:…@127.0.0.1:5432/postgres \
  python -m pytest -q
```
